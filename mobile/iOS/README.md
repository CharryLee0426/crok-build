# Crok for iOS

The phone app for crok's remote control: follow every crok session on every computer, read the transcript as it
streams, send a prompt, stop the running turn, and check the model, tokens, cost, context and plan. The relay, its API
and the device sign-in are described in [`relay/DESIGN.md`](../../relay/DESIGN.md); this app implements §1 (device
sign-in), §3 (the API) and §5 "Phone apps".

SwiftUI and Observation, Swift 6 language mode, iOS 17.0 or later (iPhone, iPad allowed). Bundle id
`dev.chenli.crok.mobile`. Data comes from the relay with [ConvexMobile](https://github.com/get-convex/convex-swift)
0.8.1. Replies render with [swift-markdown](https://github.com/swiftlang/swift-markdown) 0.9.0 (cmark-gfm) and
[SwiftMath](https://github.com/mgriebling/SwiftMath) 1.7.3 (see "Replies in Markdown").

## Open and build

`Crok.xcodeproj` is generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml` and committed,
so it opens in Xcode as is (Xcode 26 or later). After changing `project.yml` or adding files, regenerate it:

```sh
cd mobile/iOS
xcodegen generate --spec project.yml
```

Build from the command line:

```sh
xcodebuild -project Crok.xcodeproj -scheme Crok -destination 'platform=iOS Simulator,name=iPhone 17' build
```

To run on a phone, pick your team under Signing & Capabilities (the project leaves `DEVELOPMENT_TEAM` empty).

## The relay URL

Nobody types the relay's address: it is built in. The app reads it from the `CrokRelayURL` Info.plist key, set from
`CROK_RELAY_URL` per configuration, mirroring `relay/environments/` (the one place the relays are named):

| Configuration | Relay | `CROK_RELAY_URL` in |
|---|---|---|
| Debug | dev: `https://limitless-badger-727.convex.cloud` (`relay/environments/dev.env`) | `Config/Debug.xcconfig` |
| Release | production: `https://tacit-finch-29.convex.cloud` (`relay/environments/prod.env`) | `Config/Release.xcconfig` |

`//` starts a comment in xcconfig files, so the files write the address as `https:/$()/….convex.cloud`. Keep them in
step with `relay/environments/`. `mobile/scripts/build-apps.sh` builds both kinds for the Desktop folder and passes
`CROK_RELAY_URL` from those files on the xcodebuild command line: `build-apps.sh test` makes the Debug build
(`Crok-iOS-debug.app`, dev relay), `build-apps.sh prod` the Release build (`Crok-iOS-prod.app`, production relay).

To point a build at another relay (a local `npx convex dev` in `relay/`, which the simulator reaches on the Mac's
localhost; `NSAllowsLocalNetworking` permits plain HTTP there):

- at launch: `-CrokServer http://127.0.0.1:3210` (Product › Scheme › Edit Scheme › Arguments, or
  `xcrun simctl launch booted dev.chenli.crok.mobile -CrokServer http://127.0.0.1:3210`), or the `CROK_RELAY_URL`
  environment variable (`SIMCTL_CHILD_CROK_RELAY_URL=… xcrun simctl launch …`). The launch argument wins;
- at build time: `xcodebuild … CROK_RELAY_URL=http://127.0.0.1:3210` (no `$()` needed on the command line).

A sign-in belongs to the relay that issued it (the build's `CrokRelayURL`; the app no longer shows it). At launch the
app forgets a saved sign-in
(or a code still waiting for approval) from any other relay than the one this launch uses, and says "This build uses a
different relay. Sign in again." on the welcome screen: a Release build installed over a Debug one never keeps talking
to the dev relay, and a launch without the `-CrokServer` an earlier launch had signs in again. **Advanced › Device name** on the welcome screen sets the name this phone signs in under (iOS only
reveals the user-assigned device name with a special entitlement, so the default is often just "iPhone").

## Demo mode

Launch with `-CrokDemo YES` (Product › Scheme › Edit Scheme › Arguments) to use an in-memory relay with sample data:
two computers (one offline) with four projects, sessions in every state (running with a plan, waiting for approval,
waiting on a permission request the phone can answer, idle, offline, archived, and some only on a computer's disk), a
transcript with every event kind, and a failed prompt. Prompts (also to a session nobody runs on the online computer,
which a crok there then opens), Stop, session info (the stored numbers at once for a session nobody runs), answering the
permission request, reordering and fetching a listed session's history (from the online computer, after 3 s) are
simulated. The demo relay implements the same facade protocols as the live one (`Engine/RelayAPI.swift`), so
every screen runs unchanged.

| launch argument | effect |
|---|---|
| `-CrokDemo YES` | demo relay, signed in |
| `-CrokDemoSignIn YES` | with `-CrokDemo`: start signed out to show the sign-in screens |
| `-CrokDemoApproveAfter 3` | with `-CrokDemoSignIn`: the demo approves the code after 3 s |
| `-CrokAppearance light` / `dark` | force the appearance |
| `-CrokPageSize 8` | transcript page size (default 50), to try paging |
| `-CrokDemoLatency 400` | with `-CrokDemo`: every query's first answer comes after 400 ms, as over the network |
| `-CrokDemoHistory 120` | with `-CrokDemo`: 120 earlier events above the Markdown showcase, as in a long session |
| `-CrokResetState YES` | forget the Keychain credentials, drafts and caches at launch |
| `-CrokNoBrowser YES` | do not open the browser sheet when a sign-in starts |
| `-CrokServer http://127.0.0.1:3210` | sign in to that relay instead of the built-in one (also `CROK_RELAY_URL`) |

## The session list

[`mobile/DESIGN.md`](../DESIGN.md) is the contract (both phone apps alike): computers are accounts under the relay
account, projects are groups with topics, sessions are the topics.

- **Tabs**: Sessions (badge: the selected computer's unread) and Profile (the account picture as its icon, badge: the
  other computers' unread). Holding Sessions offers **Mark All as Read**; holding Profile opens the computer switcher
  (`UI/TabBarMenus.swift` puts a `UIContextMenuInteraction` on the system tab bar, since `TabView` has no hook).
- **Sessions tab** (`SessionsListView`): the selected computer (`CrokEngine.selectedComputerId`, remembered in
  `crok.selectedComputer`; by default the one active last) in the title, which opens the switcher too; an Archived
  Sessions row; one `ForumRowView` per project (rounded-square avatar, newest three topics, working / needs approval /
  the last preview, the unread total); search lists matching sessions flat. **Edit** moves projects, with Read All and
  Sort by Recent Activity in the bottom bar; a project's long-press menu has New Session, Mark as Read, Move Up / Down
  and Sort by Recent Activity.
- **Project screen** (`ProjectSessionsView`): the project's sessions as topic rows (`SessionRowView`, Telegram's topic
  bubble from `TopicIconView`), searchable, **⋯** for Mark All as Read, Reorder, Sort by Recent Activity, compose for
  a new session there. **Archived** (`ArchivedSessionsView`) lists the computer's archived sessions.

Moves show at once (`CrokEngine.reorder` keeps applying them over the relay's values until the relay confirms them) and
go back with an alert when the relay refuses; so does Mark as Read (`CrokEngine.markRead`, one `sessions:markRead` per
session). A session only on its computer's disk shows "Loading from <computer>…" when opened, or why it can't load
while the computer is offline. Rows are dimmed and "offline" only while their computer is: a session nobody runs on an
online computer takes prompts (a crok there opens it when one arrives), so it looks like any other. The order rules are
pure functions in `Core/ProjectGroups.swift`, mirroring `relay/convex/lib/projects.ts`; the computer list, the default
pick and the forum row's summary are in `Core/Computers.swift`.

## Profile and session themes

Profile (`Features/Settings/ProfileView.swift`) follows Telegram's Settings: the account, its computers (a checkmark
on the selected one) and Link a computer, Devices, Appearance, Language, the version and the developer's GitHub and X
links, Sign Out. **Appearance** (`AppearanceView`) previews a session and offers the session themes: No Theme, Classic
and Telegram's nine emoji themes, each with a light and a dark variant (`UI/SessionTheme.swift`: a four-colour gradient
and an SF Symbols doodle pattern, drawn once per size and cached; dark variants light the doodles with the gradient on
black, like Telegram's night patterns), or a photo from the library (`PhotosPicker`, stored downscaled in Application
Support, optional blur, dimmed in dark mode). A theme also sets the person's bubbles and the service capsules
(`SessionPalette` in the environment). Stored in `crok.sessionTheme` / `crok.sessionThemeBlur`;
`-crok.sessionTheme classic` on the command line picks one for a launch.

## New sessions and composer commands

As relay/DESIGN.md §5 "New sessions" and "Commands in the composer" describe: a project's "+" (and its menu's **New
Session**), or the list's compose button (which asks for the project: online computers' projects, most recent first),
opens a new-session screen ("Starts in <folder> on <computer>"); sending calls `sessions:create` and the same screen
becomes the session, with the prompt shown at once. Rows of sessions not open on their computer yet say "Starting…".
In a session, the Menu pill (or typing `/`) opens the command list: the phone's own `/new [prompt]`, `/model [name]`,
`/think [level]` (only when the model has thinking levels), `/stop` (only while running) and `/info`, then the
session's commands from `sessions:commands`. `/model` and `/think` answer with a card in the transcript (on this phone
only) whose buttons call `commands:setConfig`; with an argument they match an id, value or name by unique prefix and
apply at once. Anything else starting with `/` goes to the computer as a prompt. A computer whose crok is too old to
publish models gets "<computer> doesn't offer model choices yet. Update crok there." in the card (only an offline one
is called offline), and when `sessions:create` or `commands:setConfig` refuses, the relay's message is shown as is.
The new fields are decoded leniently, so the app also works against a relay without them. Demo mode implements all of it
(`Engine/Demo`): the MacBook offers four models, one with thinking levels whose ids differ from their values.

## Replies in Markdown

Agent replies follow relay/DESIGN.md §5 "Replies in Markdown", like the web and Android:

- `Core/MathExtractor` finds math before parsing (`$…$`, `\(…\)` inline; `$$…$$` on its own lines, `\[…\]`
  display; the pandoc rule keeps `$5 and $10` as dollars) and swaps it for placeholders; `Core/MarkdownDocument` parses
  with swift-markdown (smart punctuation off), links bare URLs itself, and turns the tree into `MDBlock` / `MDInline`
  values (single newlines are line breaks, only http/https/mailto links open, images become "🖼 alt" links and are
  never fetched, raw HTML is text except `<br>`).
- `UI/MarkdownText` draws them: headings, nested lists and quotes, task items ☐ / ☑, tables in a `TableGridLayout`
  (columns up to 260 pt, wrapping cells, a sideways scroller only when the table is wider than the bubble), code blocks
  with the language, a Copy button and highlighting, display math centred or scrolling sideways. Inline math is a
  template image in the `Text` on the baseline (SwiftMath, cached by `MathRenderer`, Dynamic Type size); math wider than
  60 % of the screen becomes a block; TeX SwiftMath cannot draw shows as its source.
- `Core/SyntaxHighlighter` is a small regex highlighter (one alternation per language, identifiers by keyword sets)
  for the languages and aliases DESIGN.md lists, coloured by `Theme.syntax` (GitHub's palette); an unknown or missing
  language stays plain.
- Streaming: blocks are `Equatable`, so while a reply grows only the blocks that changed are drawn again; parsed
  replies, highlighted code and rendered math are cached. Parsing and highlighting the showcase takes about 3 ms on the
  simulator (`MarkdownTimingTests`).
- Demo mode's "Refactor the pager's scroll model" (on Studio) ends with `relay/scripts/markdown-showcase.md` verbatim;
  `MarkdownDocumentTests` checks the copy in `Engine/Demo/DemoShowcase.swift` still matches the file.

## Staying connected

`ConnectionKeeper` (`Core/ConnectionKeeper.swift`, run by `CrokEngine`) implements relay/DESIGN.md §5 "Staying
connected": on returning to the foreground, on the network coming back or switching, and when nothing has synced for
20 s while the network is up, it refreshes the access token and pushes it (a live socket answers with fresh query
results); if nothing syncs within 10 s, `ConvexRelay` replaces its ConvexMobile client. Subscriptions move to the new
client through `QueryHub.restartAll` (screens keep their data), calls waiting on the old client are sent again, and
queries in backoff retry at once. `UNAUTHENTICATED` refreshes and replaces at once (at most every 15 s). Why it is
needed: ConvexMobile's WebSocket connect has no timeout, so a socket that died while the phone was suspended could leave
the client "connecting" for good, with every query and mutation queued behind it; and its auth bridge keeps the old
token when a refresh fails on reconnect. Only results that arrive over the socket count as synced for the title, not a
value the hub replays to a new screen.

### Checking against a real relay

`CrokUITests/LiveRelayUITests` drives the real sign-in and a real session. It is skipped unless
`TEST_RUNNER_CROK_LIVE_RELAY=1`. It launches the app with `-CrokServer http://127.0.0.1:3210`, or with
`TEST_RUNNER_CROK_LIVE_RELAY_URL` when set:

1. Run the relay locally (`cd relay && npx convex dev`) with `CLERK_JWT_ISSUER_DOMAIN` set (see `relay/README.md`).
2. Link a computer that mirrors a session titled "Fix the login redirect" and answers prompts. A fake one in the
   style of `relay/scripts/e2e.mjs` works: start/approve/poll a `computer` device, `bridge:connect`,
   `bridge:upsertSession`, `bridge:pushEvents`, and answer `bridge:inbox` by claiming each command, pushing the user
   event with its `commandId`, streaming a reply in chunks, and `bridge:completeCommand`.
3. Run the test with a screenshot folder. It writes the phone's code to `live-user-code.txt` there; approve it as the
   same person:

   ```sh
   cd relay
   npx convex run deviceAuth:approve '{"userCode":"XXXX-XXXX"}' \
     --identity '{"subject":"ios-tester","issuer":"https://placeholder.clerk.accounts.dev","name":"iOS Tester","email":"ios@example.com"}'
   ```

The test closes the browser sheet (no web app runs locally, so the page cannot load), waits for the approval, opens
the session, sends a prompt and watches clock → ✓ → ✓✓, stops a slow reply, opens the info sheet and the Devices
screen. The positions it taps for the system's sign-in alert and the sheet's close button assume an iPhone 17.

`CrokUITests/LiveReconnectUITests` checks "Staying connected" against a local relay (`TEST_RUNNER_CROK_LIVE_RECONNECT=1`):
run `node scripts/fake-computer.mjs` in `relay/`, put a freezable TCP proxy in front of the relay (while the file
`$CROK_LIVE_DIR/freeze` exists it keeps open connections silent and never answers new ones, like a socket that died
while the phone was suspended), and point the test at it (`TEST_RUNNER_CROK_LIVE_RELAY_URL`, default
`http://127.0.0.1:3290`). It writes the sign-in code to `$CROK_LIVE_DIR/live-user-code.txt` (default `/tmp/crok-live`),
then freezes the proxy, unfreezes it and expects the app back by itself, and does the same around a trip to the
background.

## Notes

- ConvexMobile 0.8.1 can drop the first value of a subscription to a query the client already holds (its
  `subscribe` forwards through a `PassthroughSubject` that is subscribed only after an async `Future` resolves).
  `QueryHub` shares one subscription per query and replays the latest value; `LiveQuery` recreates a subscription that
  stays silent for 8 s.
- Convex's HTTP API rejects a `Convex-Client` header that is not `{name}-{semver}`; the app sends `crok-ios-1.0.0`.
